# Debugging lessons

## `${2:?message}` under an EXIT trap exits 0 on bash 3.2

cause: `eval/run.sh` guarded every flag's value with `${2:?--flag needs …}`. When d4f1da4 armed an EXIT trap for the temp-directory cleanup, those guards stopped exiting red: bash 3.2 prints the message, runs the trap, and reports exit status 0, so `eval/run.sh --runs` printed `--runs needs a number` and carried on as if nothing had happened. Two eval gates had passed over it for a day because nothing called a flag without its value | proven-by: `bash -c 'set -euo pipefail; trap "true" EXIT; A="${2:?msg}"; echo after' x ''` → `x: 2: msg`, `rc=0` on bash 3.2.57; the same line without the trap → `rc=1`; `trap "true" EXIT; false` → `rc=1` and `trap "true" EXIT; exit 1` → `rc=1`, so only the expansion failure loses its status | fix: an explicit `flag_value` helper that prints and `exit 1`s; the eval gate calls four flags with no value and requires a red exit. Grep for `:?` before arming an EXIT trap in a script that has them | date: 2026-09-22

## a sandbox with no login prints the whole stream-json shape for free

cause: the eval needed the exact event shapes of `claude -p --output-format stream-json --verbose` (init, assistant, result) to write the skill-use reader and its fixtures, and a real run spends quota | proven-by: `CLAUDE_CONFIG_DIR=$(mktemp -d) claude -p hi --output-format stream-json --verbose --max-turns 1` exited 1 with three events and no API call: `system/init` (with `skills`, `slash_commands`, `agents`, `tools`), one `assistant` message (`Not logged in · Please run /login`), and the `result` object (`is_error: true`, `terminal_reason: api_error`, `total_cost_usd: 0`). The init event also showed that Claude Code 2.1.278 ships built-in skills named `debug`, `verify`, `code-review`, `simplify` and more — a `noskills` arm still has a `/debug` | fix: fixtures in `tests/gates/eval.sh` copy those shapes; `eval/README.md` names the built-in collision for the `debug` comparison | date: 2026-09-22

## run waited for its terminal to drain; the test had stopped reading it

cause: `nudge.proxy` restored the terminal in its `finally` with `tcsetattr(stdin, TCSADRAIN, …)`, and TCSADRAIN blocks until every byte already written to the terminal has been read from the other end. `RunTests._end` sent SIGTERM and then `waitpid(pid, 0)` without reading the pty master any more, so whenever a few bytes were still pending -- the echo of the knock, a stand-in mid-print -- `run` waited for the test to read and the test waited for `run` to exit, with `cat` alive between them. A real terminal always drains, so only the suite could see it, and only when the timing left bytes behind: the same test passed in 17 s in every other run | proven-by: a full run stuck 28 minutes in the agentd gate; `sample 41472` (run) topped out in `termios_tcsetattr_impl → tcsetattr → __ioctl`, `sample 39569` (the test) in `os_waitpid → __wait4`, the stand-in `cat` still `Ss+`; SIGKILL to `run` let the suite finish green. The new regression test against the old proxy: `AssertionError: run did not exit within 5 s of SIGTERM with output pending on its terminal` in 7 s; 1.6 s and green with the fix, three repeats | fix: TCSANOW at that one restore -- the way out must not depend on the reader; the test backs a real `run` up (`yes` behind a pty nobody reads, proven pending by a readable master), sends SIGTERM, and kills after five seconds so a regression fails one test instead of hanging the suite; `_end` does the same. A cleanup that blocks on a process is a hang waiting for the right timing | date: 2026-09-22

## a private TMPDIR proves nothing on macOS: mktemp ignores it

cause: the temp-leak checks pointed TMPDIR at a fixture directory and asserted it was empty afterwards, but macOS `mktemp -d`, bare or with `-t`, puts the directory under the per-user `_CS_DARWIN_USER_TEMP_DIR` (`/var/folders/…/T`) whatever TMPDIR says; only an explicit absolute template is honored. Every fixture built with a bare `mktemp -d` landed in the ambient directory, so "nothing left under the private TMPDIR" was true before any fix and the 46 directories the eval gate left per full run stayed invisible to it | proven-by: on macOS 27.0, `TMPDIR=$P mktemp -d` printed `/var/folders/kf/…/T/tmp.BdZrBjs63R` and `TMPDIR=$P mktemp -d -t x` printed `…/T/x.A12PaKbR0F`, while `mktemp -d "$P/x.XXXXXX"` landed under `$P`; the eval gate's leak check went red against the old `run.sh` with `a default offline run kept 0 directories under TMPDIR, want 4` only once `run.sh` used the template | fix: `mktmp` in `test.sh` and `eval/run.sh` pass `"${TMPDIR:-/tmp}/luciazero-<owner>.XXXXXX"`; a leak check first proves the fixture writes into the private directory (the eval gate counts the kept directories) and only then asserts the directory is empty | date: 2026-09-21

## the suite wrote hook state into the live session's state directory

cause: the hook keys its state by `${TMPDIR:-/tmp}/luciazero-verify-state-<uid>/<md5(cwd)[:12]>`, with `cwd` from stdin, then `$PWD`, then `os.getcwd()` (`luciazero-verify.sh:188`). The hooks gate's `session` checks (4c3) ran the hook under the ambient TMPDIR, and its `not json` call carried no cwd at all, so that call resolved to the checkout itself -- the directory a live Claude Code session on this checkout reads. A test run could touch the live session's markers, and an attempt to catch it in the act with a wrapper hook broke the stand-down check instead; reading the five calls did | proven-by: `printf '%s' "$PWD" | md5 | cut -c1-12` = `bd5d0a09b402`, the live state directory's name; five `luciazero-verify.sh session` calls in `tests/gates/hooks.sh` had no `TMPDIR=` in front, one of them no cwd on stdin | fix: every session call runs under `TMPDIR="${HT}"` (afaaa7b) and the tiers gate runs a green and three red children under a private TMPDIR, failing on anything left. A hook whose state lives under TMPDIR is tested under a TMPDIR of its own always, not only in the checks that look at the state | date: 2026-09-21

## a subshell on the left of || keeps running after a failing command

cause: the parallel full tier's first design ran each gate as `( gate X ) || RED=…`, and bash switches errexit off inside any command that is the left side of `||` -- the subshell body included, even when the body runs `set -e` again -- so a gate that died on a bare failing command would have carried on past it and been reported green | proven-by: `bash -c 'set -e; ( false; echo "ran in ||" ) || true'` printed `ran in ||` on bash 3.2.57, while `( false; echo "ran in bg" ) & wait $!` printed nothing and returned 1 | fix: gates run as background subshells and the parent does `wait "${PID}" || RED=…`; the tiers gate's stub install gate dies on a bare `false` and the check fails if its next line is ever seen (`set -e did not stop a gate inside its subshell`) | date: 2026-09-21

## a subshell inherits the parent's temp-directory list but never runs its EXIT trap

cause: `mktmp` records each directory in `TMP_DIRS` for the dispatcher's EXIT trap, and the full-only gates run inside `( gate X ) &`. A subshell starts with a copy of the array and of every function, but bash does not run the parent's EXIT trap when a subshell exits, and the parent never sees the copy's additions -- so a full-only gate that used `mktmp` would have leaked every directory, green or red, while the fast-tier gates, run in the parent, cleaned up. No gate had used it there yet; the tiers gate's stubs did, on purpose | proven-by: `/bin/bash -c 'trap "echo trap" EXIT; ( false ) & wait $!; ( trap "echo inner" EXIT; false ) & wait $!'` printed `inner` once and `trap` once, at the parent's exit; the tiers gate against the old dispatcher: `FAIL: a green parallel run left directories behind: luciazero-test.2v0LA0 …` (six of them), green once `gate_sub` armed the trap | fix: the subshell resets `TMP_DIRS=()` and arms `trap cleanup EXIT` before sourcing the gate -- the reset matters, since the inherited copy names the parent's config directory and buffers, which other gates are still using | date: 2026-09-21

## py_compile writes __pycache__ into the checkout whatever PYTHONDONTWRITEBYTECODE says

cause: a `python3 -m py_compile` syntax check before a full run left `__pycache__` in the tree and the packaging gate went red with `npm payload contains Python cache dir`: writing the cache file is py_compile's job, and the variable only governs the import system | proven-by: `PYTHONDONTWRITEBYTECODE=1 python3 -m py_compile m.py` in an empty directory left `__pycache__` next to `m.py`; removing the cache and rerunning the tier was green | fix: syntax-check with `python3 -c 'import ast,sys; ast.parse(open(sys.argv[1]).read())'` or compile a copy, never the checkout that a packaging run is about to stage | date: 2026-09-21

## a green metric nobody could ever see: the harness sends no exit code

cause: the hook read red/green from `tool_response.exit_code`, and the Bash response Claude Code sends to a PostToolUse hook has no such key -- `stdout`, `stderr`, `interrupted`, `isImage` -- so every green landed as `ran`: the schema 3 `redundant_green_count` was 0 in every real row, the strict gate's fast path (`last_verify == "ok"`) never fired, and the statusline never showed a green check. Every fixture in `test.sh` sent `{"exit_code":0}`, a shape the harness does not produce, so the tests proved a contract the harness never signed | proven-by: on Claude Code 2.1.278 a verify-classified command run twice with no edit between left `redundant_green=0` and `last_verify=ran`; the transcript's `toolUseResult` keys for Bash are `interrupted, isImage, noOutputExpected, stderr, stdout`; `echo verify-red-smoke; exit 3` reached only `bash-failure` (`last_verify=fail`, one `bash_count` marker, not two) | fix: in mode `bash` a response with no exit code, not `is_error` and not `interrupted`, is green, because PostToolUse only fires for a command that finished with exit 0 and a non-zero exit goes to PostToolUseFailure; an explicit exit code still wins and an interrupted command stays `ran`. 4c5 now feeds the harness's real shape and fails on the old rule with `was not read as green (got 'ran')`. A fixture is only evidence when its shape was captured from the thing it imitates | date: 2026-09-21

## a background task's completion notice wipes the turn's telemetry

cause: the harness delivers a background task notification (a finished `run_in_background` command, a forked skill, a subagent) as a UserPromptSubmit event, and the hook's `prompt` mode treats every one of those as a new turn: `rm -rf` of the session's telemetry directory and a fresh `turn_start_ms`. The stop row that follows then describes only the segment after the last notification, so a long turn that waited on a background job reports a few seconds and one Bash call. `skill_count` was low for the same reason plus plain rarity, not a missing event path: the Skill tool's PostToolUse does reach `skill` mode | proven-by: in one turn, `turn_start_ms` read `1789979931076` with 20 `bash_count` markers and 1 `skill_count` marker (a Skill tool call made in that turn), and after a background `./test.sh` finished and its notice arrived it read `1789980684189` with 1 marker and no skill marker; the harness binary at 2.1.278 carries `UserPromptExpansion` 33 times, so that path exists too | fix: the hook does not inspect the prompt text (a fragile contract with the harness) but tracks whether a turn is open: the first prompt resets the telemetry and writes a `turn_open` marker, a prompt that finds the marker is a notification and keeps everything, a clean stop removes the marker after its row is written, a stop that blocks (nudge, strict red) leaves it because the turn continues, and a session start removes a marker a crashed session left behind -- except `source: compact`, which happens mid-turn. Every marker write is fail-open. Proven by the 4c5 lifecycle checks, which fail on the same hook with the early-exit line removed (`FAIL: a prompt inside an open turn reset turn_start_ms`) | date: 2026-09-21

## every hook event paid for python3 five to nine times

cause: `luciazero-verify.sh` pulled each stdin field, each hash and the settings scan out of its own `python3 -c`, and a python3 start is ~42 ms on macOS, so `bash-start` plus `bash` added ~730 ms to every Bash tool call and `stop` ~390 ms -- latency nobody attributed to the hook because each process was small | proven-by: a counting `python3` shim on PATH: 5 (prompt), 7 (bash-start), 9 (bash, stop) spawns per event before; 1 per event after, 3 at `stop` (prelude, mtime compare, stats row); wall time per event 250-424 ms before, ~100 ms after, with `./test.sh --fast` green both sides | fix: one prelude program per event prints every derived value one per line in a fixed order with the multi-line Bash command last, read back with `IFS= read -r` and a final `cat` from one unquoted here-document -- a command containing an `EOF` line cannot end it, because the delimiter is matched on the source line before expansion. The refused-key loop is `set -f` wrapped: word-splitting a name that carries a wildcard would otherwise glob the hook's working directory | date: 2026-09-21

cause: the gate-5 runbook hashed every path under `~/.claude` and `~/.codex` into one digest and required the before and after to match. Review then found two more holes in the same instrument, both after it had already been called evidence: a symlink was recorded as a mode with no content, so retargeting one kept its row, and the harness allowance covered appearing and disappearing paths as well as changed ones, so a file created under `.claude/projects/` passed. The row now carries the sha256 of the target string. The allowance itself was the fourth defect: naming the harness's directories is a denylist, and the next run failed on two nobody had listed -- a rotating `.claude/backups/.claude.json.backup.<epoch>` and `.claude/sessions/`. A denylist of where a harness writes cannot be finished, so the rule now comes from the four installers: any difference at a path they can write fails, wherever it is, and everything else is printed as noise | date: 2026-09-09

## a backup asked "is this name free?" with a question that follows symlinks

cause: `uninstall.sh` picked its settings backup with `while os.path.exists(backup)` and then `shutil.copy2`. `os.path.exists` follows the name, so a symlink whose target does not exist answers False -- the name read as free, and the copy followed the symlink: the user's `settings.json` was written outside the config directory under a name the planter chose, and the config directory ended the run with no backup at all, one step before the file was rewritten. The shell `bakpath()` in all four installers tests `[ -e "${B}" ]`, which has the same blind spot | proven-by: an install into a scratch config dir, one dangling symlink per second for a minute at `settings.json.bak.<stamp>`, then `uninstall.sh`: before the fix the outside directory held `escaped-1` and no real backup existed; after it, the outside directory is empty, the decoys are untouched, and the backup is `settings.json.bak.<stamp>.1` with the original's bytes and mode | fix: reserve the name with `os.open(..., O_CREAT | O_EXCL)`, which the kernel refuses for anything already at the name -- a dangling symlink included -- and refuses without following it; the bytes then go through that descriptor and the name is never resolved again, `copystat` adds the mode and times, and a failure anywhere unlinks the reservation and leaves `settings.json` unwritten so the hook files stay. The shell `bakpath()` cannot reserve a name that way, but it now refuses one any symlink holds (`[ -e ] || [ -L ]`) in all four installers, which is where `install.sh` copies settings.json aside -- a check, not a reservation: the window between that test and the `cp` is still open and is tracked as roadmap R24, so the helper is a free name and never a collision-proof one | date: 2026-09-09

## quoting the hook command at the write site broke every place that reads it back

cause: `install.sh` stores each hook as a shell string, so a config directory whose name contains a space ended the command at the space and the shell answered 127 -- a hook that silently does nothing on a machine where the install reported success. The trap is that quoting the write site alone is worse than not quoting it: `--status` recognised our entries by `grep`ing settings.json for the bare path, and `uninstall.sh` matched `cmd == path or cmd.startswith(path + " ")`, so a correctly quoted entry read as somebody else's and was left behind, still pointing at files the uninstaller had just deleted | proven-by: an install into a directory named `sp2 test`, then running the stored command: `printf '{}' | sh -c "<stored>"` returned 127 before the fix and 0 after, with `install.sh --status` exiting 0 and `uninstall.sh` leaving no `luciazero-` entry; `./test.sh` green with the new 5c2/5c3 checks  The second half of the same trap: `uninstall.sh` still decided whether to run that parser by `grep`ing settings.json for the bare path, and quoting a path that contains an apostrophe splices the quote in from outside, so the directory name is not a substring of the stored command at all -- the gate answered "nothing of ours", the cleanup was skipped, and the hook files were deleted anyway (`luciazero_commands_after_uninstall=10`, `hook_file_exists_after_uninstall=False`). A matcher is not a gate: whatever decides what is ours has to be the thing that reads it | fix: one `command()` helper quotes with `shlex.quote`, which leaves a path that needs nothing byte-identical, and one `parse`/`ours` helper recognises both spellings -- including the bare form with a space in it, which `shlex` cannot parse back because it was never a valid command -- so an older install is rewritten in place instead of gaining a second entry beside it | date: 2026-09-09
